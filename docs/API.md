# API

Base path `/api/v1`. Interactive schema at `/api/docs` only when `SECURESCOPE_API_DOCS_ENABLED=true` (local development; off in production, because the page loads scripts from a public CDN). Cookie-authenticated; unsafe methods need `X-CSRF-Token`; multi-organization users select one with `X-Organization-Id`.

## App Scanning (dependency scanning, off by default)

All routes answer `404` unless `APP_SCANNING_ENABLED` is on, before any sign-in check. When `APP_SCANNING_ALLOWED_ORGS` (a JSON list of workspace ids) is set, a workspace that is not on the list gets the same `404` (browser routes, CI submissions and the creation of an App Scanning token); `[]` means none. An https site must set it before the flag can be switched on. Prefix `/api/v1/app`. Reads need `SCAN_READ`; creating needs `SCAN_CREATE` (viewers cannot).

- `/app/overview` (`GET`): plan, usage (runs and projects, with limits), supported files, whether CI tokens are available. No score or grade.
- `/app/projects` (`GET`; `POST` with `{"name"}`): per-plan project cap, `403` over it, `409` for a duplicate name.
- `/app/projects/{project_id}/archive` (`POST`): `204`.
- `/app/scans` (`GET`, optional `project_id`) and `/app/scans/{scan_id}` (`GET`): result label, counts per severity, findings, checks run and skipped, scanner versions, a limitations block.
- `/app/scans` (`POST`): JSON `{"project_id", "kinds": ["dependency"], "files": [{"name", "content"}], "ref"}`, 1 to 5 files from `package-lock.json`, `package.json`, `requirements.txt`; body limit 6 MiB (`413`). Invalid input is `422` and not counted. `Idempotency-Key` makes a retry return the same run (`replayed: true`) without a second charge. `403` at the plan limit, `429` at the per-project hourly limit. Only accepted runs are counted; failed and interrupted runs are not. The scan runs in a worker thread that holds one of the instance's processing slots until the thread has really finished (a closed connection, a restart or the 60-second hard limit cannot free it earlier); a scan stopped that way ends `interrupted` (connection closed) or `failed` (hard limit), with no findings stored, and is not counted.
- `/app/ci/submissions` (`POST`): for an `app`-scope API token (`Authorization: Bearer`), never a browser session. A `web` token, a session, an anonymous caller, a revoked or expired token, and a token whose plan no longer includes App Scanning CI all get the same `401`. Needs the `Idempotency-Key` header (`400` without; a retry returns the same run with `replayed: true` and costs nothing). Body is the strict JSON document of `app/appscan/submission.py` (`schema_version` 1, `project_id`, `checks`, `findings`), at most 4 MiB (`413`, checked while streaming). `422` with a fixed `{"code", "message"}` for malformed documents and for any document containing something that looks like a secret (the message never repeats it). `404` for a project of another workspace or an archived project. `403` at the monthly plan limit, `429` at the per-project or per-token hourly limit (`APP_CI_SUBMISSIONS_PER_TOKEN_PER_HOUR`, provisional pilot value 30; counted in the database, so every instance agrees). App tokens start with `ssa_` (Web tokens keep `ssk_`), so code from before token scopes cannot recognise them. Keys starting with `ci:` are reserved for this route and refused on `/app/scans` (`422`). The body must arrive within 30 seconds (`408`). Parsing, the secret check and building the stored result all run before anything is stored or counted, in a worker thread, one at a time per instance, so a busy answer, a timeout or a cancelled request leaves no run behind; an unexpected worker error is a fixed `500` ("The submission could not be checked.") that carries no document text: a request waits at most 10 seconds for its turn (`503`, `Retry-After`), a check that takes over 20 seconds is refused (`422`, code `too_complex`), a document with more than 100,000 values is refused before the secret scan (`422`, code `too_large`), and the slot is only freed when the thread has really finished. The token is checked at the start of the request and again inside the database transaction that records the run, so a token revoked or expired while a request is in flight is refused (`401`) and nothing is stored; a replay with a revoked token is refused too. A run that was already accepted completes. A skipped check makes the run `incomplete`, never clean. Scanner names are labelled as reported by the submitter.

## Scan states

`queued` -> `running` -> `completed` or `failed`; a queued or running scan can become `cancelled`. The database decides every race: a scan that finishes after it was cancelled is discarded, and a cancelled scan never changes finding states, scores or the overview. Cancellation works inside the one API process that runs the scan; a scan left over from a restart is marked `failed` at startup. Running a scan again creates a new scan and keeps the old one in history.

## Audit log

`GET /audit-events` is limited to owners and admins because it names members and shows what each did. Event types: `user.registered`, `auth.email_verified`, `auth.login.success`, `auth.login.failed`, `auth.logout`, `auth.session.refreshed`, `auth.password_reset.requested`, `auth.password_reset.completed`, `org.created`, `org.member.added`, `org.member.role_changed`, `org.member.removed`, `target.created`, `target.verified`, `target.verification_failed`, `target.challenge_regenerated`, `target.deleted`, `scan.created`, `scan.cancelled`, `scan.retried`, `report.exported`, `finding.status_changed`, `finding.rechecked`. The log stores no IP addresses, passwords, tokens or page content. An event whose user no longer exists has no actor.

## Findings

Every finding in a scan response carries `fingerprint` (a stable id for that check on that host), `confidence` (`high` for direct observations, `medium` for heuristic signature matches), `status`, `status_note`, `first_seen_at` and `last_seen_at`. Status is kept per organization and host. A finding becomes `resolved` only when a later **completed** scan of the same host no longer reports it; failed scans and scans that stopped at a redirect to another site never resolve anything. A resolved finding that appears again returns to `open`. `accepted_risk` and `false_positive` are analyst decisions and are not changed by scans.

## Overview

`GET /overview` answers "where do my sites stand" in one request. A site appears once it has a completed scan; failed and unfinished scans are ignored. `open_counts` and `fix_first` count only findings whose organization-level status is `open`, so resolved findings, accepted risks and false positives never count. `score_change` is the latest score minus the previous completed scan's score for the same host (null for a first scan). `history` lists completed scans' scores oldest first. The endpoint looks at the organization's 500 most recent completed scans.
