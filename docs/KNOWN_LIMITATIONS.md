# Known limitations

- Passive checks of **one page** (the final response after same-site redirects). Other paths, authenticated areas and APIs are not examined.
- Cookie checks only see cookies set on that response.
- Header presence is checked; CSP/HSTS _quality_ is only lightly assessed.
- The directory-index check is a conservative signature and can miss or (rarely) misfire.
- TLS analysis is one verified connection: certificate validity, host name, trust and the negotiated protocol and cipher. It does not enumerate supported protocol versions or cipher suites, and does not test for TLS vulnerabilities.
- Three fixed paths are requested once each (`/.well-known/security.txt`, `/.git/HEAD`, `/.env`). Detection is by content signature, so a site that answers every path with its home page is not flagged. Redirects on these paths count as "not served". Other sensitive paths are not guessed.
- A check that cannot get a usable answer (timeout, 5xx, 429) is reported as "Not checked" and never as passed; it also does not mark earlier findings of that check as fixed.
- No software-version vulnerability matching, no active testing (by design).
- The score is a heuristic, not comparable to other tools. A high score does not mean a site is secure.
- DNS pinning mitigates rebinding, but production should still use an egress proxy.
- Rate limits are in-memory and per process; single node.
- Email goes out only when a provider is configured (`SECURESCOPE_MAIL_PROVIDER=brevo|resend`); with the default `log` mailer, links are only written to the server log. A provider outage is logged and does not fail the request, so the user is not told that an email did not arrive.
- Registration reveals whether an email is already registered (409); mitigated by rate limiting only.
- Domain ownership proof expires after 180 days (`SECURESCOPE_TARGET_VERIFICATION_VALID_DAYS`, 0 = never); the site then needs a fresh challenge before it can be scanned again. Between re-verifications a domain that changes hands stays authorised. Verification is exact-host (no wildcard/subdomain scope), and only domain names are supported (no IP targets).
- Ownership verification: the HTTP-file method was confirmed once end to end on a real domain (2026-10-18, the author's own site, followed by a real scan and report). The DNS TXT method has only been tested with mocked lookups and error mapping, not against a live domain.
- DNS TXT verification trusts the resolver the server is configured with.
- Invitations are emailed, single-use links that expire after 7 days and only work for the invited address once that account has a confirmed email. If the email provider rejects a message the inviter is not told (the failure is logged); they can send the invitation again. The Team page can also not resend an invitation without typing the address again. A person with an existing account is invited the same way; there is no silent add in the interface (the API still has one).
- PDF reports are stored in the database, which counts against the free Neon storage; each is roughly tens of kilobytes. They are deleted with their scan (30, 90 or 365 days depending on the plan) and with the account.
- PDF download links last 5 minutes and are not single-use. Without `SECURESCOPE_DOWNLOAD_SIGNING_KEY` they also stop working after an API restart.
- The report renderer needs system libraries that are installed in the Docker image (`backend/Dockerfile`). The image build has not been run in the authoring environment; run `docker compose build backend` (or watch the first Render build) before relying on PDFs.
- Users cannot list or revoke individual sessions. (The audit log is available to owners and administrators through the API and the Audit page.)
- Use the app only via the configured origin (`http://localhost:8080`); other origins are refused for POSTs.
- Docker images were authored and the Compose file validated, but image builds were not executed in the authoring environment. Run `docker compose up --build` and the release checklist before relying on them.
- Website analytics counts visitors with a daily-rotating hash, so the same person on two days counts twice and "visitors" over a range is the sum of daily uniques. Days are grouped in the viewer's time zone while the hash rotates at UTC midnight, so someone active across that boundary can count twice on one local day. Views are summed in the API process (capped at 200,000 rows), which is fine for a small site but not for large traffic. Visitors who block requests to `/api/`, send Do Not Track or Global Privacy Control, or use a bot-like browser string are not counted, so the numbers are a lower bound.
- Platform Health request, latency and email figures are in memory for one process and reset on every restart; scan figures come from the database. See `docs/MONITORING.md`.
- Backups: there is no automatic backup. Neon's free plan keeps only a short restore history; take your own with `scripts/backup-db.ps1` (see `docs/OPERATIONS.md`). The backup scripts have not yet been run against the production database.
- Sign-in with Google or GitHub (`docs/OAUTH_SETUP.md`) links by verified email or provider account ID; it cannot be unlinked from the account screen yet and there is no Microsoft or Apple option.
- PDF reports use DejaVu fonts, which have no Chinese, Japanese or Korean glyphs: such characters in a finding's evidence print as empty boxes (the on-screen report and the JSON/Markdown/HTML exports show them correctly).
- Plans and limits (`docs/PLANS.md`) are enforced by the server, but there is no payment yet: a workspace is on Free unless an operator assigns another plan, and only the operator's own workspaces get the unlimited internal plan. Nothing in the product charges money.
- Scans that fail do not use up the monthly allowance, and scans are counted per calendar month in UTC, so the allowance renews at 00:00 UTC on the 1st.
