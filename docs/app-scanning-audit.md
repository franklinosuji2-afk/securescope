## 2. What is missing

| Missing piece                                                                                                                                                                                            | Why it matters                                                                                                                                                     |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Any file upload handling.** No `UploadFile` or multipart anywhere                                                                                                                                      | Every upload rule (size, count, type, storage) is new attack surface                                                                                               |
| **A request-body size limit in the application.** Only Pydantic field limits exist on JSON bodies                                                                                                        | A large body is read into memory before validation. An upload route needs its own cap, in addition to Cloudflare's                                                 |
| **A process or container boundary for risky work.** Scans, PDF builds and the scheduler run as tasks inside the single API process, limited by semaphores (`max_concurrent_scans`, one report at a time) | Nothing separates a parser bug from the API, its database connection or its secrets. `workers/` is an empty directory                                              |
| **A job queue and worker process**                                                                                                                                                                       | Not needed for web scans (seconds, one process). Needed before any long or heavy scanner runs                                                                      |
| **Manifest and lockfile parsers, a vulnerability data client, a SAST runner, a secret detector**                                                                                                         | The functional core of the module                                                                                                                                  |
| **A generic secret-redaction layer for logs and API errors**                                                                                                                                             | Logging is JSON with explicit fields only; httpx loggers are quieted. That is discipline, not a filter. A scanner that sees secrets needs a guarantee, not a habit |
| **A project (application) concept**                                                                                                                                                                      | Web scans hang off a verified host. Code has no host                                                                                                               |
| **Retention rules for source-derived data**                                                                                                                                                              | `DATA_RETENTION.md` covers scans and reports; it says nothing about code                                                                                           |

## 3. Can the existing scan model hold application scans?

Short answer: **no, not without damaging it.** Four things in the web model do not fit code:

1. **`host` is the identity of everything.** Fingerprints, finding state, comparison, the agency dashboard, badges, schedules and re-checks are all keyed by host. Storing a project name in `host` would make the web re-check try an HTTP request to it, the badge route serve it, and the agency dashboard list it as a site.
2. **Scanning requires a domain-verified `Target`.** `start_scan` refuses a host without a verified target. A repository has no domain to verify; the permission to scan is the user's own right to the code (an attestation), which is a different rule.
3. **`score`/`grade` are a heuristic about web configuration.** A grade for a dependency scan would invite the reading "A means secure".
4. **`metadata_json` is `TargetMetadata`** (status code, redirect chain, TLS). Code scans need scanner versions, advisory-database timestamp, files examined and checks skipped.

**Recommendation:** new tables for projects, app scans, app findings and their state, sharing the **shapes and enums** (`Severity`, `Confidence`, `FindingStatus`, redacted evidence, remediation) and the reporting building blocks, never the web tables. All migrations are additive; no web table changes, so Web Scanning cannot regress through the schema.

## 4. Security risks

| #   | Risk                                                                                                                                                                              | Severity        | Where it comes from                                                                                              | Required answer                                                                                                                                                                                                           |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | **Processing untrusted source on the API server.** A malicious archive or a parser/analyser bug runs inside the process that holds the database connection and production secrets | Critical        | No process boundary (section 2); free plan has 0.1 CPU and 512 MB, so heavy analysers would also starve the site | Do not process source code on the API server. Parse only small data files there (R1a), and run code analysers on the **customer's own runner** or in a separate isolated worker (section 6 of the architecture)           |
| R1a | A parser given hostile JSON or text (huge, deeply nested, or crafted)                                                                                                             | High            | New parsers                                                                                                      | Strict size and depth limits, no execution, no network from the parser, fuzz-style tests                                                                                                                                  |
| R2  | **Secrets leaking out of findings.** A secret finding's evidence ends up in the database, a PDF, a webhook, an alert email, a log line or an API error                            | Critical        | Existing alert and webhook payloads include finding titles, and evidence is free text                            | Never store or transmit any character of the secret. Store rule name, file, line, a keyed hash for de-duplication and the length class. A second server-side check rejects incoming evidence that matches secret patterns |
| R3  | **Archive attacks:** zip slip, symlinks, archive bombs, huge file counts                                                                                                          | High            | Only if archives are accepted                                                                                    | **No archives in the first release.** Single manifest files only                                                                                                                                                          |
| R4  | **Cross-customer access** (IDOR) to projects, scans, findings, reports                                                                                                            | High            | New routes                                                                                                       | Every query filtered by organization id in the repository; a route-coverage test like the one that already exists                                                                                                         |
| R5  | **Denial of service** (CPU, memory, concurrent jobs) on the free instance                                                                                                         | High            | Heavy work in the API process                                                                                    | Hard input caps, one concurrent app scan, per-workspace rate limits, a monthly allowance                                                                                                                                  |
| R6  | **Data leaving the platform.** Package names and versions are sent to a vulnerability database. For a private project, package names can be private                               | Medium          | Dependency lookups                                                                                               | Fixed destination only (no user-controlled URL, so no SSRF), documented in the privacy notice, owner decision needed (section 8)                                                                                          |
| R7  | **False reassurance.** "No findings" read as "secure"                                                                                                                             | High (trust)    | Product wording                                                                                                  | Distinct states (clean for these checks, incomplete, unsupported), a visible limitations block on every screen and report                                                                                                 |
| R8  | **Wrong or stale vulnerability data treated as clean**                                                                                                                            | High (accuracy) | Network failure, unknown ecosystem, missing versions                                                             | Unavailable data is **incomplete**, never "no vulnerabilities"                                                                                                                                                            |
| R9  | **Supply chain of the scanners themselves** (pinned versions, licences)                                                                                                           | Medium          | New dependencies                                                                                                 | Pin versions, record the version in every scan, check licences before shipping (section 8)                                                                                                                                |
| R10 | **Repository credentials** (only if GitHub integration is added)                                                                                                                  | High            | Future phase                                                                                                     | Not stored in the first release. Use the CI action, where the repository access is the runner's own                                                                                                                       |
| R11 | **SSRF from a new network client**                                                                                                                                                | High            | OSV lookups                                                                                                      | The only host contacted is a constant in code; no user input reaches the URL; redirects off by default; response size and time capped                                                                                     |

## 5. Data model implications

New, additive tables (names provisional): `app_projects` (organization, optional client, name, source kind), `app_scans` (project, scan kinds, status, scanner versions, input digests, checks run and skipped, error, timestamps, idempotency key), `app_findings` (scan, rule or advisory id, severity, confidence, package fields, file and line, redacted evidence, remediation, fingerprint) and `app_finding_states`. Source code, file contents and uploaded files are **never stored**: only digests, names, sizes and findings. Details are in `app-scanning-architecture.md`.

## 6. Recommended implementation sequence

See `app-scanning-implementation-plan.md`. In one line: design, then dependency scanning from uploaded manifest files, then code analysis and secrets through the customer's CI, then reports and history, then CI thresholds, then infrastructure files, then a controlled pilot. Server-side repository or archive upload only after an isolated worker exists.

## 7. Tests required

Listed against each phase in the implementation plan. The brief's list is covered: manifest parsing, malformed and oversized input, unsupported formats, result normalisation, secret redaction (including that no secret appears in logs, errors, reports and webhooks), timeouts and scanner failure, cross-customer isolation, role checks, plan limits, cancellation and clean-up, report consistency, no execution of project code, and a regression run of all existing Web Scanning tests.

## 8. Decisions that need the owner

1. **Run code analysis in the customer's CI (recommended) or on our own isolated server.** The second needs paid infrastructure and is not recommended for the first release.
2. **Allow dependency lookups against the public OSV database?** It sends package names and versions to a third party. Needs a line in the privacy notice. Alternative: a downloaded local copy of the database, which is large and needs storage and updates.
3. **Plan placement.** Which plans get App Scanning, and the monthly allowance (a plan change; nothing is on sale yet).
4. **Licences.** Confirm the licence terms of any rule set and database before shipping them in a paid service (for example, Semgrep's rule licence and OSV's data licence). This is not verified here.
5. **No score or grade for App Scanning in the first release** (recommended), only counts and a risk label.
6. **Name of the sections** in the menu and in marketing ("Web Scanning" and "App Scanning").
